# Devcroft (original Electron app) — feature inventory for Rust/GPUI parity

This document inventories the feature set of the original TypeScript/Electron project at `../devcroft` (Electron + React + TypeScript + Vite + Tailwind + Pierre diffs + node-pty + xterm.js/Ghostty Web) so the Rust/GPUI rewrite in this repository can achieve feature parity.
It describes **what the original does, not how the rewrite must do it**: the MCP server becomes a CLI with the same capabilities, and the home page plus navigation will be re-thought, but no capability below should be dropped silently.
Status notes (`Status:`, `Last updated:`) and file paths below refer to the original project at the time of writing; consult `devcroft/docs/desktop-app.md`, `devcroft/docs/development-workspace-architecture-plan.md`, `devcroft/docs/roadmap.md`, and `devcroft/apps/desktop/src` as the authoritative references.

Current product direction supersedes the historical task workflow: [Resources](resources.md) defines repository Markdown artifacts, sessions, and feedback. Original source-map references below are historical.

## 1. Application shell and product shape

- The original is a single Electron desktop application whose renderer is isolated from Node.js and reaches system capabilities only through a small typed preload bridge (`window.devcroft`) grouped by workspace, repositories, review, clipboard, terminal, agents, files, references, previews, tasks, and data-directory Git, with direct main-process IPC handlers and no centralized runtime-validation registry or operation authorization state machine.
- The main-process composition root creates device, workspace, repository, review (one shared `ReviewService` instance so desktop and agent mutations notify each other), agent-activity, terminal, file, editor-reference, task-workflow, data-directory-Git, clipboard, and window services, starts the loopback agent endpoint plus the authenticated loopback editor-reference endpoint where supported, and passes renderer-facing services to IPC registration.
- The renderer supports light and dark themes persisted under `devcroft-color-scheme` and written to `document.documentElement.dataset.theme`, uses semantic Tailwind v4 tokens (`bg-background`, `bg-card`, `text-foreground`, `text-muted-foreground`, `border-border`, `ring-ring`, plus `success`, `warning`, `info`, and `destructive` families) instead of hard-coded palette values, and owns its shadcn/Base UI primitives as editable source under `components/ui`.
- Global keyboard navigation uses a hold-the-modifier model (default trigger `Meta` with a 500 ms hint delay) with bindings for Agent (`A`), Diff/Review (`D`), Editor (`E`), repository switcher (`P`), Tasks (`Y`), Terminal (`/`), and Home (`H`), shows floating `kbd` hints while the trigger is held, keeps modal and alert dialogs owning their own keyboard input, and preserves tab behavior, focus containment and restoration, visible focus, accessible names, live-region announcements, contrast, zoom and long-content handling, and reduced-motion behavior in both themes.
- Cross-cutting desktop behaviors include single-instance ownership, application menu, window options and sizing (minimum 720×480, default 1200×800), per-tab error boundaries, a workspace-level error surface, sandboxed renderer with context isolation and no Node integration or webviews, strict Content Security Policy with same-origin compiled styles and no remote styles or fonts or runtime CSS loaders, and treating repository text, diffs, annotations, and generated content as untrusted.
- Original technology worth noting for parity planning includes Electron, React 19, TypeScript, Vite, Tailwind CSS v4 with source-owned shadcn components on Base UI, Pierre diffs and trees with a narrow `[data-pierre-tree-host]` and `[data-pierre-diff-host]` integration-CSS boundary, Ghostty Web as the default terminal adapter (anomalyco fork pinned to an exact commit) with a retained xterm.js adapter selectable via `VITE_TERMINAL_VIEW=xterm` behind a shared `TerminalView` interface, node-pty for PTYs, `react-markdown` with `remark-gfm` plus `shiki` for Markdown and code presentation, `lucide-react` icons, and plain JSON plus Markdown persistence with atomic temporary-sibling-plus-rename writes serialized per path in the main process.

## 2. Data ownership and portable layout

- Source checkouts own source files, commits, branches, and working-tree state, and Review, Editor, Agent, and Terminal operate directly against the linked checkout without copying source into application storage and without persisting generated diffs or terminal output.
- The user-selected portable workspace directory is a Git-backed directory of reusable plain JSON and Markdown records where Git is only a user-controlled transport and never an application database or synchronization authority, laid out as `<data-directory>/workspace.json` plus `repositories/<repository-key>/repository.json` plus `repositories/<repository-key>/reviews/<base>-to-<head>.json` plus `repositories/<repository-key>/artifacts/review-tutorials/<bounded-review-slug>--<branch-pair-sha256>.json` plus `tasks/sequence.json` plus `tasks/<task-id>/task.json`.
- `workspace.json` carries an informational `formatVersion` and optional workspace name and must never gate or reject the whole data directory on version mismatch.
- `repository.json` carries optional `key`, `owner`, `name`, `displayName`, `description`, `group`, `tags`, `cloneUrl`, and `baseBranch`, where the enclosing directory is the primary identity, the repeated `key` is a manual-inspection convenience whose mismatch produces a warning plus repair action rather than a load failure, and groups and tags remain inline strings with no category IDs or referential-integrity rules.
- Home scans `repositories/*/repository.json` with no global catalog index and reports a malformed repository record on that repository card only, while Tasks scans `tasks/*/task.json` and reports a malformed Task record independently without hiding the other Tasks.
- Device-local state lives in one OS-local file (`<electron-userData>/device.json`) and owns only machine-local values such as the portable directory path, checkout bindings, remote aliases, agent and terminal settings, recent activity, pinned repositories, last repository and last tab, editor UI state, theme, and sync schedule, uses atomic temporary-sibling-plus-rename writes serialized per path, and is resettable with `reset:device-state` without touching source or portable repositories, while `remove:local-data` interactively removes application data without deleting source repositories or the user-owned portable directory.
- Derived or volatile data is computed live rather than persisted, including Git status, branch lists, commit identities, diffs and changed-file summaries, source file contents, worktree snapshots, diff digests, terminal output, running process state, and synchronization status (`idle`, `syncing`, or `error` held in memory), with exactly one intentional narrow exception where the review-tutorial artifact stores a `sha256/devcroft-live-full-diff-v1` source fingerprint as provenance solely to detect stale guidance rather than as a reusable cache, snapshot, digest map, or history index.
- Persistence primitives stay close to `readJson(path, fallback)` and `writeJson(path, value)` with `JSON.parse`, read-time defaults for absent optional fields, preservation of unknown fields when editing where practical, two-space JSON with trailing newline, atomic replacement, per-path write serialization, ordinary errors carrying file paths and causes to the calling feature, and per-repository or per-feature degradation instead of blocking the whole workspace, with no quarantine files, document versions, migrations, recovery journals, obsolete document stores, transactions, catalog authority, retained state, tombstones, snapshots, blobs, or runtime schema registry in the production path.
- One-time Tasks version-1 reset rule: Tasks previously used a version-1 format containing definition, research, decisions, plans, and review artifacts, current builds neither read, write, nor migrate that format, users must manually back up the portable workspace and remove unneeded version-1 Task directories before adopting schema version 2, and a remaining version-1 record is reported as unsupported and is never overwritten by a version-2 mutation.

## 3. Home and repository management

- Home joins portable repository metadata with the current device checkout bindings, keeps repositories without a checkout on the current device visible with a **Link checkout** action, and supports selecting a checkout, reviewing and editing the repository key, adding or editing repository metadata, linking or unlinking a checkout, opening a linked workspace, and removing a portable repository record after confirmation.
- Repository keys are readable stable identifiers in `<owner>-<repository-name>` form such as `hossainemruz-devcroft`, suggested from the canonical Git remote, normalized to lowercase filesystem-friendly letters, numbers, hyphens, underscores, and periods, editable by the user before creation, never changed automatically on later upstream renames or ownership transfers, with collisions resolved by prompting for a different key such as `github-hossainemruz-devcroft` rather than introducing opaque identifiers, while an explicit key-rename operation remains a deferred candidate.
- Adding a repository follows checkout selection, remote URL and default-branch suggestion harvesting, editable key suggestion, creation of `repositories/<repository-key>/repository.json` in the portable directory, saving of checkout path plus remote name in `device.json`, and opening of the repository workspace, while removing a repository deletes or archives its portable directory after direct confirmation plus its device-state entry with no tombstones, retained-state records, or multi-store transactions, and linking on another device only updates that device `device.json`.
- Home listing behaviors include free-text search across display name, key, owner, name, description, group, tags, and checkout path, group filtering across `All`, each present group, and `Ungrouped`, pinned-first sorting, recent-use sorting by `lastOpenedAt`, per-repository error cards that do not block the workspace, an empty first-run state with data-directory selection, a settings dialog for changing the data directory and sync interval, a Refresh action that joins any in-flight portable-directory synchronization and then reloads Git state plus portable projections, a Git status strip when the data directory is Git-backed, and editable metadata fields for owner, name, display name, description, group, tags, clone URL, and base branch.
- Checkout selection harvests a checkout path, remote name, clone URL, owner, repository name, base branch, and suggested key from the chosen local Git checkout, and opening a repository records recency and last-tab affordances used by the workspace shell and switcher.

## 4. Repository workspace shell and navigation

- Selecting a linked repository opens a repository workspace with five primary tabs named Agent, Diff (Review), Editor, Tasks, and Terminal, keeps Agent, Editor, Tasks, and Terminal mounted while hidden so their processes and state survive tab switches, holds Review surface selection session-locally per repository rather than persisting it, and keeps the whole workspace available with an actionable Review error when the configured base ref is missing rather than blocking the other tabs.
- The workspace header provides back-to-Repositories navigation, a searchable repository switcher sorted by recent use that shows linked versus `Not linked` destinations, per-repository live Agent activity indicators, and an aggregate attention control that lists waiting Agents first under a `Needs attention` group and navigates directly to the correct Agent tab without changing ordinary repository switching semantics.
- The workspace preserves missing-link recovery, back and destination navigation, long branch labels, branch and layout controls, stale and unavailable states, persisted theme selection, per-tab error boundaries, and a global reference-admission pipeline where accepted editor code references appear as a preview above the Agent terminal, are queued as formatted text such as `At @/src/app.ts line 10 to 12` behind the Agent current input prompt, switch to the Agent tab, are acknowledged only after being written to the terminal, and have pending admissions replayed to a reloaded window without double delivery.
- All Agents across repositories contribute one transient provider-neutral activity each to the global switcher, waiting Agents appear in the adjacent attention control with a count plus `need input` affordance, and focusing an Agent tab marks its activity seen and focused while telemetry failures leave the terminal usable with status unavailable.

## 5. Agent tab

- The Agent tab runs the configured coding-agent command in a transient PTY rooted at the repository checkout, where POSIX launches go through the user login plus interactive shell (`$SHELL -l -i -c`) with shell-quoted arguments so profile and rc environment, PATH additions, Homebrew or nvm setup, aliases, functions, and tool-manager activation match the Terminal tab, while GUI-launched apps otherwise would only see a minimal environment.
- Agent execution settings include command (default `opencode`), arguments, provider preference (`auto`, `opencode`, `claude`, or `generic`, where `auto` derives the provider from the command name), and font size, configurable globally per device and overridable per repository, persisted in device-local state independently from Editor settings, and sessions support creation, input, resize, output subscription, exit notification, termination, restart, and owner-window cleanup without restoring running sessions or output after restart.
- Recognized OpenCode and Claude Code commands provide best-effort provider-aware activity through local authenticated telemetry with states `starting`, `ready`, `working`, `waiting`, `done`, `idle`, and `unknown`, unsupported or custom commands remain fully usable with status unavailable, telemetry failure never breaks the PTY, no activity, provider identities, credentials, or terminal sessions persist across restart, and the packaged Claude activity plugin is shipped as an external resource copied to a private per-launch runtime directory and removed when its terminal ends.
- The Agent tab includes a collapsible independently scrolling **Uncommitted changes** sidebar that presents the same HEAD-to-working-tree tree and Git statuses as Review uncommitted mode, refreshes on Agent-tab activation plus source changes plus manual request, routes ordinary activation to Review uncommitted mode, routes modified files to Diff because the Editor tab is a terminal (with deleted files opening in Diff with an explanation), supports Ctrl- or Option-click behavior distinctions, and uses repository-scoped monotonic navigation requests to keep asynchronous Review and Editor initialization from receiving another repository target.
- The Agent tab is the single FIFO admission point for Agent input requests from accepted code references and review-tutorial starter prompts, where each producer allocates a per-repository numeric ID, appends to that repository queue, switches that repository to the Agent tab, has the terminal consume strictly after a successful paste without synthesizing an Enter key so nothing is ever auto-submitted, and acknowledges reference-backed requests back to the main process idempotently with replay surviving renderer restarts.
- The terminal UI behind Agent, Editor, and shell orchestration depends only on the shared `TerminalView` interface with Ghostty Web as the default adapter and a retained xterm.js adapter for comparison, where each adapter owns renderer configuration, fitting, keyboard and clipboard integration including bracketed paste, focus, resizing, scrollback, scroll-wheel reporting to full-screen applications, automatic return-to-prompt on input while scrolled, and browser lifecycle, while image protocols and general mouse click or drag reporting remain intentionally deferred.

## 6. Review tab: live diff and portable comments

- The default Review comparison is PR-style `merge-base(<remote>/<baseBranch>, HEAD)` to the current working tree and therefore shows branch commits plus uncommitted changes including untracked, binary, mode, symlink, and visible submodule changes, while an explicit **uncommitted-changes** mode compares `HEAD` to the working tree and the Agent sidebar reuses the same HEAD-to-working-tree changed-file projection.
- Review resolution reads `baseBranch` from portable repository metadata, reads the remote alias from device state defaulting to `origin`, prefers `<remote>/<baseBranch>` when that remote-tracking ref exists and otherwise uses the local `<baseBranch>` ref, keeps the workspace available with an actionable Review error asking the user to fetch, create the branch, or change `baseBranch` when neither ref exists, resolves the merge base against current `HEAD`, generates changed-file metadata and file content live from Git plus the working tree, and never depends on a successful fetch for availability because fetching remains an explicit action or lightweight preference with an optional future current-branch-upstream comparison envisioned only as a separate explicit mode.
- Changed-file presentation includes navigation plus Pierre-based rendering with unified and split layouts, tree search, selection, and viewed-file state, sticky and responsive panels, per-status human-readable labels for added, modified, deleted, renamed, copied, and type-changed files, per-file additions and deletions, binary-file handling with counts, file-side descriptors with blob SHA, mode, and content kind, file-content reads with `text` versus `unavailable` for binary, too-large, invalid-text, or missing content, large-diff performance awareness, and a revision projection carrying repository identity, resolved base and head refs, change relationship (`identical`, `base-ancestor`, `head-ancestor`, `diverged`, or `unrelated`), merge-base SHA, dirty flag, diff summary with files changed plus additions plus deletions plus binary-file count, and opened timestamp.
- Review records are automatic and branch-pair based with readable keys such as `main-to-feature-terminal` derived from base and current branch names, loading the existing record when present, creating it only when the first comment is saved, updating the same record `base.commit`, `head.commit`, and `updatedAt` on new commits on either branch, re-placing comments with path, line, and context, and selecting or creating a different branch-pair record when either branch switches, with no immutable snapshots, digest mapping, revision persistence, history infrastructure, or manually selected review sessions.
- Portable comments carry key, mode (`full-diff` or `uncommitted-changes`), checkout-relative path, side (`base` or `head`), line, context, Markdown body, status (`open` or `resolved`), and creation plus update timestamps, support desktop single-comment add, body update, status set, and removal with live refresh through in-process change notifications from any surface including agent mutations, use deliberate best-effort placement that tries the stored path and line before searching nearby for stored context before showing the comment as unplaced, and treat stale or unplaced comments as a normal UI condition rather than invalid persisted data.
- Review interactions include a Diff versus Tutorial surface toggle, review-mode selector, file tree plus diff layout plus comments plus viewed-file state on Diff, comments sidebar with open, closed, filtering, editing, lifecycle, copy, and export behaviors, comment filtering across all, open, resolved, and unplaced states, comment navigation and focus shortcuts, unplaced-comment repair affordances, concise Markdown generation for **Copy comments for agent** plus one-click clipboard copy of the open feedback for the currently visible review mode, file watching with manual refresh, and live updates without manual reload after persisted mutations from renderer edits or agent calls.

## 7. Review tab: agent-authored review tutorial

- The Review tab has an accessible Diff versus Tutorial surface toggle where Diff keeps the existing review-mode selector, file tree, diff layout, comments, and viewed-file state while Tutorial swaps the file tree for a table of contents and the diff pane for a centered lesson reader, always reads the live full diff regardless of the selected Diff mode, and holds the selected surface session-local per repository without persisting it to device state.
- Tutorials are agent-authored orientation for one exact base and head branch pair over the live full diff from merge base to working tree, Devcroft never generates tutorial content itself, and **Generate with Agent**, **Update with Agent**, and **Regenerate with Agent** all switch to the Agent tab and insert one editable non-submitting single-line starter prompt that the user can amend before submitting to the configured coding agent.
- The agent workflow contract requires the agent to inspect the complete tracked diff and repository context with its own tools, independently enumerate every untracked path with `git status --porcelain=v1 -z --untracked-files=all` because ordinary `git diff` omits untracked content and the bounded changed-file manifest may be truncated, read every untracked text file, and then submit one strict typed tutorial document through the agent API so there is exactly one optimistic-concurrency contract with the renderer remaining read-only for tutorial content.
- Tutorial storage uses one portable JSON artifact per exact base and head branch pair at `<portable-data-directory>/repositories/<repository-key>/artifacts/review-tutorials/<bounded-review-slug>--<branch-pair-sha256>.json`, where the readable branch-pair slug is bounded to 80 ASCII bytes, the full SHA-256 of the length-framed exact branch names prevents distinct branch pairs that normalize to the same slug from sharing an artifact, the service derives the path so callers never submit or receive one, the file holds a versioned JSON envelope with service-owned metadata including branch-pair identity, merge base, source fingerprint, and generation timestamps plus the agent-authored structured document, one atomic temporary-sibling-plus-rename write replaces envelope and document together, and the persisted artifact contains no diff snapshot, absolute path, provider or model identifier, prompt transcript, or test output.
- Tutorial freshness recomputes a `sha256/devcroft-live-full-diff-v1` fingerprint from the checkout on every load using branch pair, merge base, changed records in stable path order, worktree bytes hashed for every head-side file the diff represents including binaries and symlink targets, untracked files, and review-visible submodule state, compares it with the generation-time fingerprint, exposes states for `missing`, `fresh`, `stale` with previous content remaining readable behind a prominent warning and never presented as current, `malformed` reported explicitly and replaceable only with an exact regeneration against the artifact ETag, and `no-changes`, does not invalidate on commits, staging, or unstaging that leave merge-base-to-working-tree content unchanged, and refreshes on surface activation, window focus, debounced watched checkout content edits, data-directory Git events, successful agent writes, and manual refresh rather than on a portable-workspace watcher.
- The tutorial document uses authoring dialect `devcroft-review-tutorial-v1` with a closed exact registry of visualization nodes comprising Markdown prose plus `callout` for warnings, traps, or key reviewer insights plus `flow` for linear dependency, execution, ownership, or lifecycle sequences plus `comparison` for contrasting two mechanisms, states, or reviewer assumptions plus `codeWalkthrough` for explaining one short source excerpt with numbered observations plus `timeline` for implementation, correction, migration, or lifecycle history plus `reviewChecklist` for concrete source-grounded verification tasks with interactive device-local state plus `knowledgeCheck` for checkable questions with interactive device-local state plus `glossary` for repository-specific terms plus `fileTree` for dependency-ordered or concept-grouped review paths, where adding a node requires coordinated schema, renderer, capability, and skill updates and unknown types are never guessed into a known schema.
- The core workflow needs only agent-API configuration while an optional `review-tutorial` agent skill lives at `integrations/opencode/skills/review-tutorial/` in the original repository, must be installed manually by copying or symlinking it into the global agent skills directory so it is available while the Agent tab is rooted at any linked repository, owns editorial procedure only while storage paths, source identity, and concurrency remain exclusively in Devcroft services and agent tools, and serves as a distribution asset rather than a runtime dependency that never bypasses service contracts.

## 8. Editor tab and code references

- The Editor tab runs a persisted per-repository terminal editor in the checkout through the same PTY session machinery as Agent and Terminal with `nvim .` as the default command so the checkout directory opens instead of an empty buffer, keeps browsing, editing, search, and save-conflict handling inside the user-chosen TUI editor, holds sessions transiently in memory with input, resize, output, exit, and owner-window termination without restoring running sessions after restart, and persists only the command, arguments, and font size in per-repository device-local state independently from Agent settings through an Editor settings panel with font-size bounds.
- Editor launches on POSIX systems run through the user login plus interactive shell (`$SHELL -l -i -c`) with the same environment inheritance as Agent, and only editor terminals receive three service-owned runtime variables identifying the loopback reference URL plus per-launch bearer token plus repository key, where inherited copies of those variable names are stripped before injection so nested processes cannot forward stale credentials, no endpoint or variables exist on Windows, and startup failure only logs that editor references are unavailable while every other feature keeps working.
- The code-reference endpoint starts with Devcroft on macOS or Linux as an ephemeral `127.0.0.1` loopback HTTP route accepting only loopback-origin requests with matching `Host` and `Origin` metadata and authenticating every request with a per-launch cryptographically random bearer token, accepts code-reference requests identifying repository key plus checkout-relative file path plus one-based line range, snapshots the referenced file through the repository-scoped file API, forwards it to the renderer, never modifies files, uses bounded request bodies plus bounded pending admissions plus idempotency entries with TTL plus close timeouts, and has focused unit coverage for the reference service, terminal environment handling, preload subscriptions, IPC handlers, and application-level routing.
- The repository-scoped file API supports reading a repository-relative forward-slash text file with an opaque content-hash revision token, watching per-repository file changes with `modified`, `deleted`, and `unavailable` kinds where `unavailable` means live watching ended unexpectedly and consumers should fall back to manual refresh, enforcing relative-path validation with traversal protection, limiting readable files to 4 MiB of strict UTF-8 text, skipping configured directories, and snapshotting accepted references for Agent delivery.
- Accepted references appear as the most recent preview above the Agent terminal, queue formatted text behind the Agent current input prompt, switch to the Agent tab, acknowledge back to the main process only after the queued text has actually been written to the terminal with idempotent acknowledgement and replay of pending admissions to a reloaded window without double delivery, and carry request identity so exactly-once handling is assertable.
- The Editor-adjacent Markdown preview flow surfaces accepted Markdown previews in a dialog with a table of contents and lesson-style reading behavior, while the earlier Monaco-based source-exploration vision with file tree, file opening, file-name and text-content search, multi-file editing ergonomics, language-aware symbols and navigation, large-file and external-change handling, search-result previews, formatting, and language-server integration remains a deferred roadmap candidate rather than shipped behavior.

## 10. Terminal tab

## 11. Agent API (MCP server in the original; CLI in the rewrite)

- The original starts a stateless Streamable HTTP agent endpoint at the fixed loopback address `http://127.0.0.1:8756/mcp` whenever the desktop application runs, binds only to `127.0.0.1` with strict `Host` and `Origin` validation and no CORS headers, exposes thirteen focused tools with resource-first grammar (`<resource>_<verb>[_<qualifier>]`), composes one request-scoped tool server per request over the same shared `TaskWorkflow` and `ReviewService` used by the desktop with serialized mutations and no retained session, Task, or client state between requests, and notifies open desktop views through in-process change notifications after every successful persisted mutation.
- The endpoint is unauthenticated by design in the first version and therefore must never be exposed beyond loopback, any local process running while Devcroft is open can call it, a second Devcroft instance cannot bind the same port so only the primary instance serves agent traffic, production never falls back to another port because the address is part of the documented configuration, startup failure from an occupied or unbindable port is never fatal and instead reports an error status with the conflicting port while every other feature keeps working, OpenCode must be configured manually with the documented remote URL because Devcroft never edits agent configuration files, the endpoint exists only while Devcroft runs and tool calls fail when Devcroft is closed or still starting, and a per-device bearer token remains the recommended future hardening.
- Review-comment tools comprise `review_comment_list` listing comments for the repository current branch-pair review defaulting to open comments across both review modes with returned, open, and resolved counts, `review_comment_set_status` atomically setting previously listed comments to open or resolved, and `review_comment_delete` atomically deleting an explicit list of previously listed comments, where listing returns repository-relative paths plus current placement plus original anchored line plus concurrency tokens, batch mutations validate every listed comment review key, mode, and update timestamp before writing so stale requests can never overwrite newer human feedback, duplicate IDs are rejected, deletions require an explicit non-empty list, agents can read comments plus change status plus delete an explicit list but can never create or edit comment bodies because comment bodies stay human-owned.
- Review-tutorial tools comprise `review_tutorial_get` loading the current tutorial state for the repository current branch-pair review with branch-pair identity and source fingerprint, bounded repository-relative changed-file manifest with total file count and explicit truncation flag, diff summary, tutorial status, parsed structured document when present and parseable, artifact ETag including the ETag of a malformed artifact, valid metadata, render capabilities, and source-inspection instructions, plus `review_tutorial_write` atomically replacing the tutorial with optimistic concurrency requiring the source fingerprint plus artifact ETag exactly as returned by the get call where the ETag is null only when the last read reported no artifact, rejecting stale source with `review_changed` and concurrently updated artifacts with `tutorial_changed`, validating the exact authoring dialect and block types advertised by render capabilities with ordinary prose in Markdown content nodes and rich content in typed nodes, using the same shared `ReviewService` and path derivation as the desktop with no arbitrary artifact path accepted or returned, and requiring the agent to inspect the complete merge-base-to-working-tree tracked diff plus repository context plus independently enumerated untracked files itself because the bounded manifest is orientation only.
- The rewrite replaces this loopback MCP endpoint with a CLI that must preserve the same thirteen operations, filters, validation rules, atomicity guarantees, optimistic-concurrency contracts, human-owned comment-body boundary, tutorial source-inspection contract, error vocabulary, and live-refresh semantics adapted to a non-running-desktop model.

## 12. Portable Git synchronization

- Users may synchronize the portable workspace with ordinary Git tools where local files remain immediately usable when fetch, merge, or push fails, Devcroft maintains no local mirror, retained state, tombstones, synchronization journals, automatic scheduling, application-specific conflict-resolution UI, setup, mutation, adoption, ownership, or operation journals, and unusual Git states are left for ordinary Git tooling.
- The built-in best-effort synchronization action stages Devcroft portable files, commits them with `chore(devcroft): sync portable data` when there are changes, fetches and integrates upstream changes with one documented strategy that rebases onto the exact fetched commit, pushes the result, stops and displays a sanitized Git error on conflicts or authentication problems, treats the working directory as the immediate source of truth, and keeps synchronization status in memory rather than persisting it.
- Git status and synchronization outcomes travel as structured renderer state rather than inferred human-readable Git stderr, including kind (`repository`, `not-repository`, or `unavailable`), branch, detached flag, upstream, ahead and behind counts, staged, unstaged, untracked, conflicted, and Devcroft-owned change counts, in-progress operation (`merge`, `rebase`, `cherry-pick`, `revert`, or `bisect`), blocker with sanitized guidance for `detached-head`, `no-upstream`, `conflict`, `operation-in-progress`, `unrelated-changes-block-rebase`, `merge-commit-in-unpublished-range`, or `rewritten-upstream`, sync phase with trigger plus last-attempt plus last-success plus error for `missing-identity`, `authentication`, `network`, `timeout`, `push-rejected`, `git-unavailable`, or `unknown`, selectable sync interval of 2, 5, 15, or 30 minutes, monotonic selection generation used to ignore events from a previously selected directory, and a reload-required flag marking outcomes where a rebase may have changed portable files so Home, Tasks, and Review projections must reload.
- Synchronization supports manual and scheduled triggers, joins the single in-flight synchronization when Refresh is pressed on a Git-backed directory before always reloading Git state plus portable projections regardless of outcome, persists the schedule bound to the canonical data directory so switching directories never carries an active schedule, re-arms the scheduler after persisted schedule changes, surfaces state in the home header status strip and settings dialog with sanitized guidance such as resolving or aborting the Git operation in the data directory before refreshing, and emits change events used for live projection reloads.

## 13. Supporting services and device behaviors

- Workspace and device services own portable-directory discovery and repository scanning, `device.json` loading and saving, directory-selection generation tracking, portable-access gating, JSON and text-file helpers, serialized writes, and development-only reset semantics.
- Repository service owns checkout selection dialogs, remote-identity parsing, repository-key suggestion plus validation plus collision handling, metadata cleaning and merging, checkout existence checks, link, unlink, remove, open, pin, metadata update, and per-repository warnings and errors.
- Git runner owns process execution, result modeling, status parsing, branch discovery, diff parsing for numstat plus raw diff records, merge-base resolution, changed-file metadata generation, file-content retrieval, submodule visibility, and actionable missing-ref errors.
- Terminal service owns PTY session lifecycle with creation, input, resize, output, exit, and termination, per-kind settings resolution for agent, editor, and shell terminals, provider-aware launch coordination, editor-only reference-environment injection, shell command resolution with POSIX versus Windows defaults, font-size bounds, and owner-window cleanup.
- Agent-activity service owns provider resolution, OpenCode and Claude adapters, activity reduction, live activity listing, seen and focused reporting, change fan-out, and transient provider runtime resources.
- File, watcher, preview, and reference services own repository-scoped reads, per-repository watching, Markdown preview projection, loopback reference admission with pending plus idempotency handling, and exactly-once renderer delivery.

## 14. Verification, packaging, and development commands

- `pnpm dev` starts the desktop app in development mode, `pnpm build` builds it, `pnpm check` runs formatting plus linting plus typechecking plus unit tests plus smoke tests, `pnpm lint` lints with zero warnings allowed, `pnpm typecheck` typechecks the desktop app, `pnpm test` runs unit tests with Vitest, `pnpm test:smoke` runs desktop smoke tests, `pnpm format` and `pnpm format:check` write or verify Prettier formatting, `pnpm reset:device-state` removes only the device-local state file, `pnpm remove:local-data` interactively removes application data without touching source repositories, and `pnpm ui:add` adds justified primitives through the pinned shadcn generator.

## 15. Explicit non-goals, deferred work, and rewrite notes

- The original intentionally provides no compatibility with old persisted data, no general-purpose database or document-store framework, no runtime validation of every request or persisted document, no release-grade hostile-input hardening, no seamless synchronization conflict resolution, no terminal-session restoration after restart, no persisted source snapshots or complete diffs except tutorial provenance, no provider-specific Git hosting integration, and no multi-user permissions or shared-workspace access control.
- Deferred roadmap candidates that are not shipped behavior include repository-key rename UX, better recent and pinned repository navigation, editable base branch plus remote alias plus shell plus agent settings beyond what already exists, clearer first-run and link-checkout guidance, more persistent editor layout and cursor state, explicit fetch action plus optional lightweight fetch preference refinements, better comment navigation and unplaced-comment repair, review filtering and viewed-file workflow refinements, optional current-branch-upstream comparison as a separate mode, very-large-diff performance work, language-aware symbols and navigation, safer large-file and external-change handling, richer search previews, multi-file editing ergonomics, optional formatting and language-server integration, shared reusable agent prompts and configuration, final supported-platform and packaging commitments, and automatic portable-repository synchronization until a manual path proves useful and predictable.
- For this Rust/GPUI rewrite, preserve every shipped behavior above while deliberately changing two integration points: expose the thirteen agent operations as a CLI rather than a loopback MCP server, and re-think the home page plus repository navigation rather than cloning the Electron layout pixel for pixel.
- Suggested parity acceptance is therefore behavioral rather than visual: a portable directory from the original opens here, every repository operation works, Agent plus Editor plus Terminal run interactive PTYs rooted at the checkout, Review reproduces both live modes plus comments plus Markdown export plus tutorial states and transitions, Tasks reproduces the compact lifecycle plus validation plus destructive-delete semantics plus cross-surface refresh, portable Git sync preserves manual plus scheduled semantics plus structured errors, and the CLI reproduces every agent operation with equivalent validation, atomicity, concurrency, and human-owned-content boundaries.
